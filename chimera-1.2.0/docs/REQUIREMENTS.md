# RU → Foreign: требования к частному VPN

Дата: 18 октября 2026. Версия: 1.0. Назначение: самостоятельное задание агенту разработки нового решения.

## 1. Цель и границы

Создать простое решение для владельца и небольшого круга близких: один российский VPS принимает подключения, определяет маршрут и выпускает российский трафик непосредственно в интернет; один зарубежный VPS выпускает остальной трафик. Клиент знает только RU. Выбор второго перехода и правила разделения выполняются на сервере. На старте ориентироваться на 7 пользователей и до 20 устройств; это проектная ёмкость, а не обещание пропускной способности.

Обязательные результаты: серверная часть, минимальная тёмная веб-панель, Telegram-бот, выдача и отзыв профилей, готовые установочные и настроечные скрипты для обоих серверов, краткая инструкция эксплуатации.

**Указание агенту: не думать о тестировании как о части проекта и не закладывать его в архитектуру, задачи, сроки и результаты. Не создавать автотесты, тестовые стенды, unit/integration/e2e/smoke/load-тесты, тестовую CI, планы тестирования и отдельные этапы QA. Пользователь самостоятельно выполняет ручной проход и сообщает о проблемах; агент исправляет их итеративно. Не заявлять о проверенной работе на реальной сети без фактического запуска.**

Контроль доступности транспорта во время работы, ограничения конфигурации и откат ошибочного применения являются функциями продукта, а не отдельной программой тестирования. Они нужны для переключения путей и сохранения доступа к серверу.

Не включать биллинг, публичную регистрацию, собственные мобильные клиенты, Kubernetes, микросервисы, третий VPS и обязательные платные внешние сервисы.

## 2. Архитектура

Клиент → VLESS REALITY либо AmneziaWG → RU gateway → единая политика:

- RU_DIRECT → прямой выход с RU VPS.
- FOREIGN → выбранный защищённый межсерверный транспорт → foreign VPS → интернет.
- BLOCK → отказ в соединении.

Оба входных протокола используют одни и те же правила. Не делать два независимых маршрутизатора с расходящимися списками. Логический пользователь имеет отдельные учётные данные на каждое устройство и протокол.

Рекомендуемый минимальный стек: Ubuntu LTS с зафиксированной поддерживаемой версией; sing-box на обоих узлах; AmneziaWG на RU; nftables и policy routing; Python/FastAPI + Jinja2 + SQLite для панели; aiogram для Telegram; Caddy для HTTPS панели; systemd для запуска. На старте без контейнеров, чтобы не добавлять взаимодействие Docker NAT и маршрутизации. Совместимые версии всех компонентов фиксируются в release manifest; не ставить непроверенный latest автоматически. Возможности из документации будущих релизов не переносить в старый бинарник.

AWG завершается отдельным интерфейсом на RU. Его пользовательский трафик направляется в TUN sing-box через отдельную таблицу маршрутизации. VLESS завершается непосредственно в sing-box. Перехват ограничен AWG-интерфейсом/подсетью; default route самого хоста не менять. Не включать глобальный auto_route без ограничения области действия. TCP и UDP обязательны; произвольные IP-протоколы и сквозной ICMP через прокси не обещать.

На foreign нет пользовательской панели, Telegram-бота и конечных пользовательских учётных записей. Он принимает только межсерверные соединения с отдельными секретами.

## 3. Вход на RU

### VLESS

- VLESS + REALITY поверх TCP, при поддержке выбранных компонентов — flow xtls-rprx-vision.
- Основной порт RU TCP/443; UUID отдельный на устройство.
- В профиле только RU endpoint, публичные параметры REALITY, идентификатор пользователя и параметры совместимого клиента. Никаких адресов и секретов foreign.
- Выдача URI, QR и краткой инструкции. Подписка с отзывным токеном допустима для поддерживающих её клиентов.
- Профиль/инструкция предусматривают полный TUN/VPN-режим клиента: режим одного браузерного прокси не покрывает весь трафик устройства.

### AmneziaWG

- Базовая целевая версия — AWG 3.1 с явным указанием совместимых приложений и их версий; не смешивать параметры разных поколений AWG.
- Собственная UDP-точка входа, например UDP/443, и отдельный ключ на устройство.
- Обфускация включена, секретные параметры генерируются при установке; одинаковые демонстрационные ключи запрещены.
- Выдача готового .conf и QR, где размер позволяет; клиенту не предлагается вручную редактировать параметры.
- Для полного маршрута использовать соответствующие AllowedIPs. IPv6 должен также перехватываться и блокироваться сервером либо полноценно поддерживаться, а не оставаться прямым обходным маршрутом.
- Не обещать бесшовное переключение VLESS ↔ AWG на телефоне: это два отдельных профиля, между которыми пользователь переключается в совместимых приложениях.

## 4. Межсерверная передача и резервирование

### Обязательный основной путь

VLESS + REALITY / TCP/443, RU выступает клиентом, foreign сервером. Отдельные UUID, пара ключей REALITY и short ID; эти данные не совпадают с пользовательским входом. Выбранные SNI/handshake target должны соответствовать требованиям актуальной реализации REALITY. Для sing-box включить требуемый REALITY-клиентом uTLS и поддерживаемый fingerprint; не принимать конфигурацию, заведомо приводящую к «uTLS is required by reality client».

REALITY уменьшает явные признаки протокола, но не скрывает IP foreign, объём, время и длительность соединений. Нельзя обещать невидимость DPI или неотличимость от браузера. VLESS сам по себе не является шифрованием: защищённый транспорт обязателен.

### Обязательный резервный путь

Hysteria2 / UDP/443 с TLS и Salamander obfuscation. Отдельные пароль авторизации и пароль обфускации. Сертификат проверяется: допустим доверенный сертификат или предусмотренное выбранной версией закрепление доверенного сертификата; insecure=true запрещён. Самоподписанный сертификат допустим при явном доверии к нему на RU и предусмотренной ротации.

Этот вариант добавляет другой транспорт без третьего сервера и без второго прокси-ядра. Salamander не выдавать за полноценную имитацию браузерного HTTPS. Если UDP между хостерами недоступен, резервный путь не будет работать — это эксплуатационное ограничение, а не повод выпускать foreign-трафик напрямую.

### Политика путей

- Активен один путь для новых соединений; балансировку по пакетам не делать.
- Режимы: Auto, принудительно основной, принудительно резервный. В принудительном режиме не переключать маршрут самовольно.
- Auto предпочитает основной путь. При нескольких последовательных неудачах эксплуатационного запроса через него выбирает исправный резервный. TCP connect к порту недостаточен: запрос должен пройти через транспорт и зарубежный выход.
- Начальные настраиваемые значения: интервал 30 секунд, 3 неудачи для отключения, минимум 120 секунд между переключениями, возврат после 5 успехов основного. Для исключения зависимости от одного внешнего адреса использовать два назначения, оценивая ошибки раздельно.
- Это приоритетный failover, а не выбор минимального ping. Не подменять его без пояснения URLTest с иной семантикой.
- Состояния: unknown / available / unavailable / disabled. При старте с unknown разрешена попытка основного защищённого пути; прямой fallback исключён.
- Переключение может оборвать существующие сессии. Сохранение TCP-сессий при смене транспорта не входит в требования.
- При отказе обоих путей FOREIGN блокируется, RU_DIRECT остаётся доступен. DNS следует той же политике.

Два транспорта на одном IP защищают от части протокольных отказов, но не от блокировки IP, аварии VPS или общего маршрута провайдера. В первой версии не покупать дополнительные серверы. Модель данных должна допускать второй foreign endpoint без переделки пользователей и панели. Позже наиболее полезен второй VPS у другого провайдера/ASN; дополнительный порт на том же IP не равен независимому пути. XHTTP/TLS можно рассмотреть позднее как другой TCP-транспорт, но не добавлять сейчас отдельное ядро ради третьего варианта.

## 5. Правила определения RU и foreign

«Российский сервис» — управляемая категория доменов и адресов, а не только зона .ru или физическое положение IP. Российский сервис может использовать иностранный CDN, а иностранный сервис — российский адрес. Абсолютно точной автоматической классификации нет.

Приоритет сверху вниз:

1. Блокировка доступа пользователей к служебным интерфейсам, loopback, link-local, metadata провайдера, приватным подсетям и другим VPN-клиентам; отдельно разрешить только DNS gateway и явно заданные пользовательские сервисы.
2. Ручные правила администратора с явным порядком: BLOCK, FOREIGN или RU_DIRECT для домена/суффикса/CIDR. Служебные запреты обычными правилами не отменяются.
3. Домен из поддерживаемого RU-services списка → RU_DIRECT, даже если адрес CDN иностранный.
4. Если достоверное доменное назначение известно и не относится к RU-services → FOREIGN; не переопределять его одним совпадением российского IP.
5. Если домен неизвестен, IP из RU-IP списка → RU_DIRECT.
6. Всё остальное → FOREIGN.

Списки брать из документированных источников с лицензиями, фиксировать источник и версию. Базовый список должен поставляться вместе с релизом, чтобы первый запуск не зависел от скачивания списков через ещё не поднятый туннель. Обновления атомарные, не чаще раза в сутки; при недоступности источника остаётся предыдущая версия. Отдельная кнопка отката. Настройки пользователя обновлением не затираются. Не заменять это устаревшими полями GeoIP/Geosite, если выбранная версия ядра требует rule-set.

Показать админу простую форму «домен/IP → предполагаемое правило и маршрут». Для домена выводить, что результат зависит от реально доступного имени и резолвинга; не выдавать симуляцию правила за фактический маршрут сессии.

## 6. DNS, IPv6 и утечки

- Профили указывают DNS gateway. Обычный клиентский DNS TCP/UDP 53 внутри VPN направляется в управляемый DNS независимо от указанного адреса резолвера.
- RU-домены разрешаются через RU-resolver; прочие через resolver, доступ к которому идёт по foreign. Кэши и выбор upstream должны сохранять разделение политик. При отказе foreign нельзя молча использовать RU-resolver для foreign-доменов.
- Bootstrap DNS для endpoint, сертификатов и системных служб отделён от клиентского DNS и не образует рекурсию через ещё не установленный туннель. Для межсерверного dial предпочтителен явный IP с отдельным TLS server name.
- Использовать DNS-сопоставление и доступный sniffing без MITM и подмены пользовательских TLS-сертификатов. Учитывать TTL и неоднозначность общих CDN-IP; при конфликте выбирать FOREIGN.
- DoH/DoT приложений и ECH ограничивают видимость домена. Не обещать серверу распознавание любого имени; при отсутствии имени применяется IP-ветка. В инструкции объяснить отключение пользовательского Secure DNS, если требуется более предсказуемая классификация.
- Первая версия: IPv4-выход; IPv6 внутри VPN явно отклоняется. Профили должны захватывать IPv6 либо требовать клиентский kill switch/блокировку IPv6. Простого отключения IPv6 на RU недостаточно, чтобы предотвратить обход VPN на устройстве.
- MTU задаётся конфигурацией, с консервативным значением для AWG; предусмотреть изменение без пересоздания всех пользователей. Не блокировать необходимые ICMP-сообщения PMTU на серверных интерфейсах.

## 7. Изоляция и fail-closed

Прямой выход разрешён только как осознанное решение RU_DIRECT. Запрещён общий MASQUERADE для AWG-подсети на внешнем интерфейсе, который позволит обойти маршрутизатор при его остановке. AWG forwarding по умолчанию закрыт и допускает только передачу в обработчик; direct-соединения создаёт сам шлюз после классификации. Остановка sing-box не должна открывать запасной путь ядра в интернет. Одного final=FOREIGN в конфиге недостаточно без firewall.

SSH, apt, системное время, загрузка обновлений и обычные службы хоста используют основной RU uplink. Исходящие соединения самого шлюза привязываются к uplink/маркируются так, чтобы не попадать обратно в TUN. Область TUN и nftables должна исключать петли.

На foreign ограничить межсерверные порты адресом RU, если адрес постоянный; оставить возможность безопасно обновить allowlist. Служебный доступ защищён ключами. На обоих узлах закрыть лишние порты. Панель и бот работают без root; привилегированные действия выполняет локальный helper с фиксированным набором операций и без произвольных shell-команд.

Fail-closed защищает от утечки при отказах, а не от злонамеренной компрометации самого RU gateway. На RU заканчивается первый туннель; сквозная защита содержимого приложений зависит также от HTTPS и других протоколов самих приложений.

## 8. Веб-панель

Обязательна тёмная тема по умолчанию, адаптация под телефон, русский интерфейс. Небольшие серверные HTML-страницы без тяжёлого SPA.

Пользователь: вход, список своих устройств, добавить устройство в пределах лимита, выбрать AWG/VLESS, скачать профиль, открыть QR, прочитать короткую инструкцию, отозвать устройство. Повторное получение профиля не создаёт новые ключи. Ротация — отдельное действие.

Администратор: создать/заблокировать пользователя, выдать одноразовое приглашение, задать лимит устройств, отозвать профиль/все профили пользователя; управлять правилами маршрутизации, видеть активный межсерверный путь и состояние компонентов, переключить режим Auto/основной/резервный. Не показывать «всё работает» только по факту запуска процесса.

Вход по логину и паролю с безопасным хешированием; приглашение одноразовое и с ограниченным сроком. Сессии HttpOnly/Secure/SameSite, защита CSRF и ограничение попыток. Непубличный адрес административной страницы допустим, но не заменяет авторизацию. Пользователь не видит чужих устройств и topology foreign.

RU TCP/443 занят VLESS: панель по умолчанию HTTPS на отдельном настраиваемом TCP/8443. Предусмотреть выпуск/обновление сертификата, например HTTP-01 на TCP/80 с доменом панели. Не назначать два процесса на один TCP/443 и не предполагать, что разные DNS-имена сами решают конфликт. UDP/443 для AWG не конфликтует с TCP/443.

## 9. Telegram-бот

Один бот обращается к тому же backend и базе, что панель. Long polling вместо публичного webhook. Использование только в личных чатах. Привязка к пользователю по одноразовому приглашению и числовому Telegram user ID; username не является идентификатором доступа.

Кнопки: «Мои устройства», «Добавить устройство», «Получить профиль», «Инструкция», «Отозвать устройство». Администратору доступны приглашения, блокировка и уведомления о длительном отказе foreign/смене пути с ограничением частоты. По умолчанию профиль выдаётся через короткоживущую одноразовую HTTPS-ссылку; отправку .conf/QR непосредственно в чат разрешить только явным выбором пользователя. Бот не отправляет SSH-ключи и межсерверные секреты.

При недоступности Telegram существующий VPN продолжает работать, панель остаётся самостоятельным способом выдачи. Для самого бота предусмотреть явно выбранный исходящий маршрут: прямой или через локальный foreign proxy; выбор не меняет маршрутизацию остальных системных служб. Не пытаться скрытно переключать весь хост ради Telegram.

## 10. Учётные данные и согласованность

Сущности: User, Device, Credential, Invitation, RouteOverride, Gateway, Transport, AppliedRevision. Создание устройства идемпотентно; параллельные нажатия в панели и боте не создают дубликаты. Состояния изменения: pending, applied, failed. Профиль выдаётся только после применения нужной конфигурации; ошибка не маскируется статусом успеха.

Отзыв убирает AWG peer и VLESS UUID, инвалидирует ссылки и подписки; активные сессии должны быть завершены доступным ядру механизмом, при необходимости контролируемым перезапуском с указанием воздействия на других пользователей. Удаление файла профиля или токена подписки само по себе не является отзывом доступа.

Приватные ключи устройств, если хранятся ради повторной выдачи, шифруются ключом вне БД; права на файлы минимальные. Ссылки и секреты не писать в access logs. Запросы DNS, полную историю сайтов и содержимое трафика не журналировать. Хранить события управления, ошибки компонентов и смены путей с ротацией.

Падение панели, БД или бота не останавливает работающий data plane. Применение конфигураций сериализовано; хранится последняя рабочая ревизия и доступен откат. Обновление пользователя не должно требовать изменения foreign, поскольку его учётные данные заканчиваются на RU.

## 11. Установка, настройка, обслуживание

Поставка включает один репозиторий и готовый release archive. Один setup-конфиг содержит адреса узлов, uplink, домен панели, порты, выбранные версии, DNS, режимы маршрутов и лимиты. Секреты вводятся отдельно/генерируются, в Git не попадают.

Обязательные команды/скрипты:

- install-foreign.sh: зависимости, оба защищённых транспорта, firewall и systemd; создание пакета сопряжения.
- install-ru.sh: AWG, sing-box/TUN, политика маршрутизации, firewall, панель, БД, бот, TLS и systemd.
- configure.sh: применение локальных изменений без переустановки.
- pair.sh: импорт параметров foreign и настройка RU; закрытый пакет либо ограниченный SSH-канал, не публичная URL со всеми секретами.
- update.sh и rollback.sh: обновление закреплённого релиза и возврат предыдущей версии/конфигурации.
- backup.sh и restore.sh: зашифрованная копия БД, конфигураций и необходимых ключей; пароль/ключ восстановления хранится отдельно.
- status.sh: понятный статус компонентов и активного пути; диагностический вывод без секретов.

Скрипты повторно запускаемы, не пересоздают ключи без команды ротации и не дублируют правила. Не делать flush всего nftables. Не сбрасывать OS, SSH и посторонние сервисы. Если существующая сеть несовместима, остановиться с конкретным описанием конфликта, а не перезаписывать её.

Изменения firewall/маршрутов применять с таймером автоматического отката, отменяемым владельцем после сохранения доступа. Не отключать существующий способ SSH-входа автоматически. Пакет сопряжения удаляется после импорта; в документации описаны отзыв и перевыпуск. Скачать дистрибутив можно с рабочего компьютера и загрузить на VPS вручную: установка не должна полагаться исключительно на доступ VPS к GitHub.

## 12. Порядок разработки и комплект результата

1. Зафиксировать совместимые версии, модель конфигурации и скрипты foreign + основной защищённый путь.
2. Реализовать RU gateway, оба входа, общую политику, DNS и firewall fail-closed.
3. Добавить резервный транспорт и эксплуатационный автомат переключения.
4. Реализовать единый backend управления пользователями/устройствами и минимальную тёмную панель.
5. Подключить Telegram к тому же backend.
6. Собрать установку, сопряжение, обновление, откат, резервную копию и короткое руководство.

На каждом шаге выдавать работающий код и конфигурации, а не заглушки. Разработка не требует выделенного этапа тестирования. Для ручной эксплуатации предоставить обычные инструкции запуска и диагностики, без отдельного тест-плана.

Результат: исходники, release archive, пример setup-конфига без секретов, закреплённые версии, комплект скриптов, шаблоны профилей, README установки и восстановления, список фактически поддерживаемых клиентских приложений и честно обозначенные ограничения. Не включать обещания гарантированного обхода всех российских блокировок и автоматического распознавания всех российских сервисов.
